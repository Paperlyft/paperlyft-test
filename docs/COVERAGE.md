# Acceptance coverage

The catalog in [`scenarios/catalog.ts`](../scenarios/catalog.ts) records the intended acceptance surface and labels each case as automated, planned, manual, or dependent on an external fixture. Only cases with a real browser test path are counted as automated. A catalog entry does not establish that its live target, account, fixture, or provider is available.

Current automated coverage is intentionally small: the public home and anonymous private-API denial canaries; desktop keyboard navigation and axe smoke; a 390px upload workspace and axe smoke; bulk-import modal defaults; owner/member visibility; exact website-script copy; an actual private-record reader denial; and a customer-host journey that loads the actual script, resolves a real published PDF link, opens its dialog, and displays an accessible document frame. Real account tests verify their configured subject, tenant, and role before assertions. These tests use the configured live PaperLyft target and do not intercept product API responses. The reader denial requires a retained unpublished record; customer-host integration additionally requires a public HTTPS fixture host and a published document linked from that host.

The live suite also contains guarded journeys for processing settings, multi-PDF uploads, idempotent import preparation, paid public URL conversion, five configured account roles, cross-tenant document denial, and an opt-in random real-document corpus. Conversion and real-document processing require explicit paid-processing authorization; their presence in the catalog does not authorize execution. The broader catalog includes multilingual and mixed-script documents; scanned, layout-heavy, encrypted and malformed files; website discovery and sitemap behavior; review, approval, publication, withdrawal and version history; tenant isolation and SSRF; billing limits; retries and concurrency; accessibility; privacy; and customer website integration. These remain gaps unless their status explicitly says automated.

Each live test has a stable scenario ID in its title. `@live` marks a real target test, `@mutation` marks tests that alter product state, and `@canary` marks the bounded cases eligible for the separately enabled production canary. Only explicit read-only `@canary` scenarios list production as an environment; processing and mutations remain local or staging only. Skipped tests and offline fixture-lab behavior do not count as live acceptance evidence.

To inspect the current gap list, filter `scenarioCatalog` by `status !== 'automated'`. Planned scenarios need a supported fixture and real target journey before they can move to automated coverage. The lab includes one synthetic grayscale image-only scan, which demonstrates raster-only input but establishes no OCR accuracy; `document.scanned-ocr` remains a gap. Arabic, Chinese, and Hindi corpus fixtures remain unavailable until licensed sample material and required fonts are available.

## Product discovery limits from source inspection

Current website discovery starts with an HTML page or sitemap and extracts static HTML anchors and sitemap `<loc>` values. It does not run page JavaScript, call JSON APIs, or inspect iframe contents. A `.pdf` linked from an accepted page may be fetched from another host, but HTML crawling is restricted to the seed site's allowed origins. SharePoint pages that require authentication, POST-based search, or private links are outside the public-import workflow.

Source inspection shows a 60-second deadline, up to 1,000 discovered PDF URLs, 20 HTML pages, and 10 non-HTML requests (including robots.txt). The crawler reads sitemap declarations but ignores robots.txt `Disallow` rules. It ignores `<base href>`, catches fetch errors without reporting each one, and does not provide a definitive completeness/truncation summary. It extracts static anchors and sitemap `<loc>` values; it does not execute JavaScript, enumerate JSON APIs, or inspect iframe content. Cross-domain PDF links may be fetched, while HTML crawling is restricted to seeded/original origins. Authenticated pages and POST-based search are outside the public-import workflow. These are source-inspection findings, not observations about any provider's current site. They prevent a claim of complete-site discovery or “all PDFs” coverage.

## Implemented preparation journeys (not yet run)

`pnpm e2e --suite discovery` uses the real PaperLyft import-preparation UI against a dedicated public HTTPS fixture host. The six HTML profile journeys save reports and assert expected source URLs and page totals, then verify monitoring is disabled and no item has an admitted document ID; they stop before conversion admission. They are implemented but have not been executed. Source inspection predicts known failures for Granicus and Joomla query-download handling and Revize `<base href>` resolution; those remain acceptance gaps, not passing coverage.

Preparation saves state, so use a dedicated `adminA` account and a local or staging target with `PAPERLYFT_ALLOW_MUTATIONS=1`. Set `PAPERLYFT_PUBLIC_FIXTURE_BASE_URL` to the dedicated public HTTPS lab origin, and start that lab with `PAPERLYFT_LAB_DISCOVERY_ONLY=1`. Before importing, the test checks `/lab-capabilities` for `providerDiscoveryIsolated: true`; this prevents unrelated root-sitemap links from contaminating expected results. No paid-processing flag is needed. Production is unsupported. No offline fixture check is counted as product coverage.

The WordPress multisite REST profile and custom JavaScript/API migration profile are catalogued but not tested by this suite: the current crawler does not enumerate JSON APIs or execute page JavaScript. All profiles are synthetic delivery-pattern examples, not vendor compatibility tests. The `imports.discovery.*` catalog status means a browser journey is implemented; it does not mean that journey has been run or passed.
